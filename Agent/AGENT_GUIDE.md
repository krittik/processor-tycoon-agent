# Processor Tycoon agent interface

## Bootstrap: inspect before playing

Replies include a separate `notifications` section containing newly captured native transient popup messages (competitor CPU releases, factory completions, contracts and other popup text) and, in a multiplayer session, chat messages from other players (`chat_message`). Read it alongside the command result: a competitor release is context, not proof of why demand changed. Messages survive their on-screen disappearance, within a 512-item in-memory ring; `cursor`, `historyTruncated` and `captureAvailable` make limits explicit. Disabled/suppressed native notifications are not fabricated. Blocking dialogs remain in their existing dialog API.

CLI merges notifications across its internal operation polling into the final output. Different agents should use distinct `--session` values. Delivery cursors advance when a response is prepared (not guaranteed network acknowledgement); after a lost response, use `notifications --since LAST_SEEN_ID` to replay retained messages. Replay does not consume automatic delivery. `notifications --since ID --limit N` keeps only the most recent N matches and `--type competitor_cpu_released` (or `game_notification`, `chat_message`; comma-separated for several) filters by type; the reply's `notifications.filter` reports matched/returned/retained counts. CLI compositions use stable per-composition sessions (`watch-cli`, `pulse-cli`, `situation-cli`, ...) so they never push your own session's cursor out of the bridge's 64-session table (which would make the next ordinary reply carry the whole backlog). IDs are scoped to the status `instance` and reset on game restart; messages include date/scene for context across loaded campaigns. Capture begins only when this version starts: no retroactive recovery from a prior process. Ordinary notifications do not stop time advance.

`pt-agent --help` is a short offline entry point; `guide` is this full reference. `prompt` prints the game description and agent instructions without a machine-specific path. The first successful CLI connection to each game process also prints that prompt to standard error before the command response; subsequent calls do not repeat it. JSON responses remain on standard output. Add `--compact` to any command to drop repeated explanatory boilerplate, empty notification blocks and duplicate structured catalog cells (each row keeps its `display`); warnings, notes, errors and data remain. Short window/dialog `scope` identifiers are kept (only long explanatory `scope` sentences are dropped). No AGENTS.md, source tree, IDE or computer-use integration is needed to play once the agent has the CLI path.

Run `pt-agent status` first. This is a read-only diagnostic even with the game closed: `ok: true` means the diagnostic succeeded, NOT that gameplay is available. Read `host.processRunning`, `host.modInstalled`, `bridge.state` and `game.state` / `game.canReadCampaign` / `game.next`. Top-level `state` and `paused` on a live bridge describe agent connection/pause, not game time.

- `not_running`: `pt-agent launch` starts the visible client and waits up to 30 seconds (`--timeout 1..60`). It never creates/loads a campaign. A timeout returns `started_not_ready`; read status, do not repeatedly launch. An existing process returns `already_running` without a duplicate.
- `main_menu`: no campaign is loaded. Use `game session-new-preview` to open/read setup choices; `game session-new-start` explicitly starts it. Or `game save-list`, then `game save-load EXACT_SAVE`. Campaign commands return `no_campaign_loaded` instead of empty/misleading data.
- `campaign`: player-visible game date is available; `game desktop-read` returns current money/date. This does not guarantee every action is unblocked: resolve native dialogs through `game dialog-read` / `game dialog-choose`.
- `gameplay_not_ready` / `scene_not_ready`: scene transition or unavailable native UI; check status again, not another Start/Load. Unknown readiness is not a claimed loaded campaign.
- `bridge_unavailable`: game process exists, but bridge is missing/starting/unresponsive. Do not spawn another game. If persistent, inspect `BepInEx/LogOutput.log`.
- `installation_not_found` / `mod_not_installed`: CLI placement or mod installation needs fixing; follow the returned next step.

`status` never navigates or resumes the game. When an accepted mutation loses its response, its outcome may be unknown; diagnostics are not permission to replay it. `launch` is a local CLI command, not a Game API route.

## Start here: Game API for supported work, Generic UI for everything else

Use `game` commands for ordinary supported play: semantic names, physical units, compact catalogs and action readback. Generic is only fallback for unmapped/modified UI or diagnosis. Game API can read entire open player-browsable catalogs including offscreen cards without manual pan/scroll; native game rules and player-accessible knowledge remain authoritative. Explicit start/develop/send/sign commits; preview/read/list does not. The 106 Game commands cover inventoried ordinary workflows in English 0.2.16a5, with representative native lifecycle tests and independent gameplay acceptance. This is not a guarantee for every combination or future version.

### Ordinary gameplay quick reference

Market preferences are player-visible knowledge, not something to infer solely from sales. The native Market Share chart tooltips explain each segment's priorities, recommended package types, current recommended price and optimal power. `game market-share` includes them as `guidance.items` and `guidance.complete`. Read All/Desktop/Mobile filters for their corresponding segments. If `guidance.complete` is false, do not read missing entries as no preferences; generic hover/observe or a screenshot is the fallback. Dynamic recommendations must be read live, not copied as permanent constants from an example.

Numbers in examples demonstrate syntax, not recommended prices/designs or a strategy. Read the current native specs, unit cost, market/recommended prices and finances before making economic choices. Production `balance` in units/day is stock flow, not monetary profit; product profit is not total company profit. A default/bankruptcy warning with remaining days is not itself game-over: read the native situation and decide how to continue.

Before committing a CPU project, run `game cpu-review EXACT_DRAFT_NAME --target-market "Desktop" --planned-price 100` (choose the actual market and intended price). It collects the current draft, finance, production, research, market guidance and rival tables. The review temporarily closes and reopens its CPU draft through native controls and verifies its contents; if another window blocks this route, it reports gaps and leaves that window alone. Inspect `evidence`, `gaps` and `riskSignals`; these are observations and simple comparisons, not a demand forecast. An enabled Develop button does not establish demand, profitability or funding safety. If the draft is materially behind or the credit scenario is poor, reconsider the design or research. `cpu-develop` without a review does not press Develop. To proceed, use the returned `reviewId` and explain your choice with `--decision-reason`; if `gaps` is nonempty, explicitly add `--accept-missing-evidence true` or resolve the gaps and review again. The agent may choose a risky strategy, but the CLI never chooses one for it.

### Economic pitfalls

These describe native mechanics, not a prescribed strategy. Verify them in your own game.

- Negative cash is debt against Available Credit, and interest is charged every month on all of it. `desktop-read` `finances.debt` shows the debt, the estimated credit limit and the implied monthly rate. The credit limit grows over time, including jumps such as around the new year; `finances.creditTrend` measures that growth from finance reads in the current game process (it resets on new game, load or restart). That growth funds early spending, but interest on all debt eventually cancels it: `finances.debt.debtWhereInterestEqualsLimitGrowth` and `headroomGrowthAfterInterestPerMonth` show where new headroom stops. A CPU that cannot compete with current rivals, financed with debt, may never be repaid; the resulting interest can leave no room for research or a better CPU.
- `finances.default` (desktop-read, product-pulse, time-advance results) is the native top-bar "Bankruptcy in N days" countdown, which starts when Available Credit falls below zero. The countdown runs to zero and does not clear early when credit recovers. The company survives only if Available Credit is zero or more when it ends. The native warning popup may appear only once, so later defaults can be silent; time-advance and projects-wait wake with `default_started` for this reason. Emergency line or division sales can be disabled or small, so check their previews before relying on them.
- A line's native Production figure (production-capacity, expansion preview) is monthly output for the reference die in `detailTooltips` (for example a 30 mm² die at 85% yield), not per day. Output scales roughly inversely with die area. `cpu-review` `evidence.capacityEstimate` scales it to the draft and your current lines: compare it with the units/month a contract or market target needs before planning around them.
- CPU project cost depends only on the selected components, not on frequency, die size or performance, so a weak interim CPU costs as much as a strong one on the same components.
- Every CPU project pays the full listed cost of all its components again; earlier development of the same architecture, package, node or memory does not make later projects cheaper. Check the next draft's cost instead of assuming a cheap follow-up.
- Contract acceptance probability, required lines and fines are visible only when evaluated against a released CPU (`contracts-list --cpu`). On Impossible they can be low and far beyond starting capacity, and shortfalls carry per-unit fines, so do not design around contract prices you cannot yet evaluate.
- `cpu-review` `evidence.runway` projects credit at completion and, on a shortfall, the estimated default start and 120-day deadline. Severe signals (`far_below_market_performance`, `baseline_credit_shortfall`, `company_in_default`) are listed in `requiredAcknowledgements`, and `cpu-develop` refuses with `risk_acknowledgement_required` until `--acknowledge-risks KIND,...` names every one. This is a deliberate speed bump, not a ban: reconsider first, and explain in `--decision-reason` how each risk is handled. `evidence.competitivePosition` compares the draft with the best current rival and the best MIPS-per-dollar rival in the target market (your own CPUs excluded). Rivals keep releasing during your development time.
- Native production automation can assign far more or far fewer lines than demand needs. Check `production-read` after every release and after automation changes.
- Production line accounting: a product row's `productionLines` (and product-pulse `productionLines`) is the TOTAL producing that CPU, including lines the game dedicates to its active contracts. `manualLines` is the Production slider value, which is exactly what `product-production NAME --lines N` sets; `contractLines` = total - manual; the slider (and `--lines`) accepts 0..(current manual lines + unassigned lines), shown as `availableRange.maxLines`; contract lines are never set with `--lines`. When more lines are assigned than the factory can run, the row's `requestedTotalLines` (compact views: `requestedLines`) is what is assigned and `productionLines` the effective count; `capacityLimited` flags it. The split is read from the native slider (`linesBasis: native_slider`).
- Production keeps consuming wafers when demand falls, and unsold units become stock. Watch `--stock-above` or reduce lines when demand drops below production. Retiring a product sells its stock at roughly unit cost.
- Price response can be non-monotonic because of market segments: crossing a segment's recommended price can raise demand as well as collapse it, and the response can shift at the start of a month. Probe both directions and re-probe after month starts and competitor releases.
- Rival generations often arrive in waves (several stronger CPUs within days), which can erase a product's demand overnight. Profits during a product's window are temporary: funding the next competitive CPU (research and development) and a reserve usually matters more than capacity for the current product, whose lines sit idle once it is obsolete.
- `game cpu-variants --die-sizes 10,15,20 [--frequencies 3,3.2] [--planned-price P]` (CLI composition; frequencies in MHz, suffixes such as 3.2GHz accepted) previews each combination on the open draft and reports MIPS, temperature against the safe limit, yield, unit cost now and later, project cost, estimated units per line and for all current lines, and gross margin if every unit sells at the planned price. It then restores the draft. `cpu-review` adds `evidence.marketSupply` (the target market's unserved share and units) and an informational `supply_constrained_market` signal when at least 10% of demand is unserved. While supply is short, output per line can earn more than a few extra MIPS, so compare die sizes by monthly units × margin; die size is fixed once development starts.
- `cpu-review` `evidence.marketOverview` and `game situation` `marketOverview` list every market's size, unserved share and units, plus segment recommended prices (Desktop High/Mid/Low End, Industries), so a market choice can be compared rather than assumed. The architecture decides the market (CISC Desktop, RISC Industries).
- Larger wafer research lets existing lines upgrade automatically (Production "Upgrade lines"), multiplying their output far more cheaply than new lines. CPU development does not block research; `cpu-develop` notes when no research is running.
- Responses carry throttled `advisories` (at most once per game date; each condition when it first appears and then every 30 game days while it persists; never on the save-load/new-game reply itself, because the native finance panel is not yet populated when loading completes): `thin_reserve` (Available Credit below your last previewed CPU project cost, below three months of outflows, or debt near the interest trap), `in_default`, and `research_idle`. The CLI merges advisories from all internal polls into the final output. They are warnings, not actions.
- Game over: when the company is bankrupt, EVERY reply carries `companyBankrupt` (`source`: `native_game_over` when the Game Over window is open, `multiplayer_session` when a Multiplayer session keeps you watching), `status.game.companyBankrupt` is true, `desktop-read` finances include `bankrupt` and `game situation` flags `bankrupt`. Stop playing that company: nothing new can start. The top-bar "Bankruptcy in 0 days" text alone does not mean the company is still playable.
- Markets move in boom and bust cycles: rival releases, rival price cuts and economic events can move demand within days. The game announces releases but not price changes. `game market-changes` (and the `marketChanges` section of `game situation`) compares the Desktop, Mobile and Industries tables with the stored snapshot (tools/competitor-prices.json; the old tools/market-snapshot.json is imported once) and lists rival price changes, new and no-longer-listed CPUs, plus CLI-synthesized notifications (see "Parsing, market signals, portfolio guards, pricing tools" below).
- New products start with low popularity that grows with sales over months; strong sales of old weak CPUs come from accumulated popularity.
- `game situation` (CLI composition, reads only) summarizes finance (reserve in months of outflows, debt trap distance, default, `headroomBeforeDefault`), research (active, funding, sharp time drops), exact `lines`, products (demand, production, stock) and, per market (Desktop, Mobile, Industries), your CPUs against the best and best-value rivals, plus `recentRivalPriceMoves` (last 30 days), `recentMarketSignals` and `newRivalCpus` (popularity of rival CPUs first seen in the last year). Its `flags` include `in_default`, `low_reserve`, `near_debt_trap`, `research_inactive`, `research_underfunded`, `idle_lines`, `overproduction` and `product_behind_market` (under 70% of the best rival's MIPS). It never acts. `production-expand` applies the same acknowledgement rule as cpu-develop: when construction would take Available Credit below zero at the current balance, or the company is in default, it refuses with `risk_acknowledgement_required` until `--acknowledge-risks baseline_credit_shortfall[,company_in_default]` is given. `cpu-review` adds `competitive_position_unknown` as a severe signal when competitor specs could not be collected (for example because other windows were open); close those windows and review again.
- Research speed is not proportional to funding, so total cost per technology differs from monthly cost. Compare total cost against the cost of the delay; `game research-funding-compare --funding-percents 25,50,100` previews several levels and restores the original.
- Research gets cheaper and faster once rival companies have researched a technology: a technology's displayed time can drop sharply overnight. `game situation` (research.timeDrops) and the notifications list report `research_time_dropped` when a displayed time fell more than the elapsed days. Waiting for this keeps you a generation behind, so weigh it against your product window.
- Available Credit is the debt limit minus debt (native rule); positive cash is NOT part of it. Money you can spend before default is Available Credit + cash on hand (`headroomBeforeDefault` in situation, products-pulse finances, desktop-read `finances.headroom`, cpu-review `evidence.runway`). The `baseline_credit_shortfall` acknowledgement (cpu-review, production-expand) and the `thin_reserve` advisory use this headroom.
- Price segments: each market segment has a native recommended price (market-share tooltips; situation `segmentRecommendedPricesByMarket`). The CLI treats a CPU as belonging to the highest segment whose recommended price is at or below its price. Crossing such a threshold can move demand a lot in either direction; product-price warns with `segment_threshold_crossed`, and `segment_price_changed` notifications report when a recommended price moves (a product near a boundary can switch segment without any price change).
- Popularity: a new product starts with low popularity (native highest popularity x100 in the sales sheet, products-pulse `popularity`), so its demand dips at launch and grows with sales over months. A new product that is strictly worse than your own older product (lower MIPS at a higher price) may never gain popularity; product-price warns with `dominated_by_own_product` / `cannibalizes_high_volume_sibling`.
- Overflow: when one of your products is out of stock, its unmet demand (products-pulse `unservedDemandPerMonthEstimate`; last month's `missedSalesLastMonth`) overflows to your other CPUs or to rivals. A price cut on a product that already sells everything it makes (`supply_limited`) adds no units; more output needs lines.

At release, inspect `projects-release-read` and set an intentional price; the form's default price may differ sharply from current market guidance. After release, inspect `production-read` or `product-pulse` to confirm actual assigned lines, capacity and stock; native automation may assign zero lines. Let the game advance only as needed to observe updated demand, then compare sales and whole-company balance with factory, research and interest expenses. A product that has demand can still lose money.

Use names/options returned by the API. Named flags are preferred; JSON/file/stdin remains an alternative. Booleans take explicit true/false. `--help` (including after a command) prints this guide locally without dispatching game input. Stdout is one JSON result; after 3 seconds of waiting, stderr prints one JSON diagnostic with the operation ID. Long operations are queryable by ID, so do not blindly retry after a CLI timeout. Use --no-wait to receive the operation ID immediately; while time-advance is running, inspect that operation or use time-cancel instead of queuing more game actions.

Run gameplay commands sequentially, including reads: `cpu-options`, finance, market and research reads can open different native windows. Do not use Promise.all/parallel shell calls for them. Await each operation before the next command; otherwise a preserved CPU draft or picker may cover the next requested window.

For current money and monthly balance use `game desktop-read` (`status.money`, `status.balance`, `finances`). `finances` includes Available Credit and every native balance-tooltip row, including zero rows; expense magnitudes may be displayed without a minus sign. These are latest desktop month-equivalent rates, not historical month totals. Do not infer insolvency from cash alone or from the disabled Bank app. Credit availability is not itself a loan action or a statement of borrowing terms. `game finance-read` is selected-company historical income/expense flow; its separate `playerCurrentFinances` always refers to YOUR company. `game statistics-read` is lifetime totals. These views are not interchangeable.

Research planning: `game research-list --status all` and `game research-topology` expose future choices/prerequisites. Once started, research responses include `controls` with the current funding range and innovation availability. Use `game research-set --funding-percent N` to trade monthly spending against speed; changing speed also changes the spending duration, so monthly cost alone does not establish overall efficiency. `game research-set --innovation-effort true --funding-percent N` enables higher funding (native current-build maximum 500%, versus normal 100%) and chooses the desired value. The toggle alone does not raise funding. Returned `before` and `active` compare native monthly spending/speed/time, not hidden formulas or hypothetical simulation; edits persist. Market responses include `analysisOptions` linking preferences, filtered specs/commercial metrics, Inspector, history, own sales and finance. Known market-sales navigation mismatch remains unresolved; use market-catalog --view market for available commercial metrics and disclose missing data.

Window policy: leave the latest working workspace visible; on a domain change, close only prior workspaces opened by the agent. Player-owned windows, unfinished editors/drafts and dialogs are preserved. `game window-open` explicitly pins the requested workspace until separately closed. Physical player input releases automatic ownership only of the window it touched (the window under the click/scroll pointer, or holding keyboard focus); that window is then the player's and is never auto-closed, while other agent-opened views stay eligible for cleanup. `game window-list` marks each visible window: `agentOpened: true` (opened by an agent command and not touched by the player since), `autoClose: true` (closed automatically on the next domain change), `dialog: true` (a native dialog, including any unknown window holding a native time-blocking popup trigger) and `blocksTime: true` (a known form or draft, such as the CPU designer "Create CPU", that keeps game time paused while it is open; it is NOT a dialog: dialog-read lists it only under `timeBlockingWindows`, dialog-choose refuses to press its buttons, and it is never closed automatically; close it with `game window-close "Create CPU"` or finish it before advancing time). Its `coveredWindows` lists open workspace windows hidden completely behind other windows (`covered: true`, same flags); they are otherwise invisible to observe/window-list. Domain-change cleanup also closes agent-owned read-only views that are still covered by a window the agent does not own (through their own native Close button, never while a native popup or the Pause Menu is open). Responses report `closedAgentWindows` when cleanup occurs. Generic never auto-cleans windows. An explicit `window-close` of a read-only workspace view that another window (for example a CPU draft) covers partly or completely (listed in `coveredWindows`) uses that view's own native Close button (result `wasCovered: true` when it was hidden), but never while a native dialog or the Pause Menu is open; a covered draft/form is refused rather than closed blindly. `game window-tidy` closes every visible or covered read-only workspace view (Analysis, Research, Production, Inspector, Contracts, Contract Manager, Business, Email, Statistics, and Manage Lines only when `agentOpened`, because it can hold a pending expansion/sale draft), frontmost first with retries, and lists what it kept (`keptOpen` with scope and reason: CPU drafts/editors, the release form, dialogs, negotiations, settings, save/load, Pause Menu, a player's Manage Lines; never closed automatically). The CLI does the same stale-view cleanup automatically before `cpu-review`, `watch-advance` and `products-pulse`, and retries a `product-pulse`/`production-read`/`product-list` once after closing stale views when it failed as covered (`closedStaleWindows` in the result); add `--keep-windows true` to skip it. The compositions `situation`, `market-changes`, `cpu-variants`, `products-pulse` and `watch-advance` close the views they opened themselves (`closedWindows` / `workspace`). The decorative blue Agent cursor only visualizes real visible targets; it does not control the OS mouse or delay inputs, and offscreen semantic actions do not fabricate screen clicks.

`game watch-advance EXACT_PRODUCT --days N` is a CLI composition of one-day native `time-advance` and `product-pulse` calls. Several products: `--products "A,B,C"` (optionally together with the target) or `--all-products`; they are read from one Production read per day (`production-read`) with company finance from each native advance. The watch opens Production once with its baseline read (whose normal domain cleanup also closes agent-owned leftovers such as a Settings window with its Pause Menu) and then pins it (explicit window-open) so the daily advances do not close it and no day reopens it; each daily `time-advance` also returns the open Production rows (`includeProduction`), so a watched day costs one bridge call (`workspace.rowsReadWithAdvance: true`); it closes it at the end if the watch opened it or an earlier agent command had left it open (`workspace` in the result; a player's own Production window stays open), after closing stale read-only views first (`--keep-windows true` skips that). Company finance comes from each native advance or from the same Production read. It requires at least one explicit guard. Choose any of `--demand-up-percent P`, `--demand-down-percent P` (compared with both the prior day and the starting day), `--min-demand-to-production R`, `--max-demand-to-production R`, `--stock-above UNITS`, `--credit-below DOLLARS`, `--balance-below DOLLARS`, `--stop-on-competitor-release true` or `--stop-on-default true` (stops while the native bankruptcy countdown is active); `--speed 1|2|3` is optional. Summaries include `defaultDaysLeft`. Demand, ratio and stock guards apply to every watched product; each trigger names its `product` and `triggeredProducts` lists them. Out of stock counts as stock 0, a product with 0 lines has production 0, and the ratio guards skip a product while its production is 0 (the ratio is undefined; `demandToProduction` is null) instead of firing or failing. A metric that a product's row does not expose is listed in that product's `unavailable` and its guards are skipped; the watch refuses to start only when no requested guard can be evaluated at all. A product that disappears from Production stops the watch with `product_missing`. A guard already true at baseline stops at 0 days. The command stops after the first game day crossing a guard, a native popup/project wake, player input, or an unverified operation; it reports the stopped date, triggers, a compact per-product summary `products` (lines, manual/contract lines when known, demand, production, stock, outOfStock, demandToProduction, demand change since start) and, for one product, the previous `current`/`baseline` snapshots. Native popups (Research Completed, Project Completed / CPU release form, factory-completed or other blocking popups, CPU release/other forms covering the rows, Pause Menu) never end as `pulse_unavailable`: whether the advance woke on them (`popup`, `popup_already_open`) or they appeared after the day (`popup_after_day`), the watch stops cleanly with `outcome: game_event`, `wakeReasons`, `dialogs` (name, scope, choices, text; `source: covering_window` for an unrecognized form or draft that covered the read, wake reason `window_blocking`, no choices; `kind: "form"` for an open form that keeps time paused such as the CPU designer, wake reason `form_open`, no choices) and, for the release form, `releaseForm` plus the projects-release command. ### Parsing, market signals, portfolio guards, pricing tools

Numbers: every display number is parsed suffix-aware ("1.15K" = 1,150, "149.31K" MIPS = 149,310, "$1.95K", "2.05B") with decimal arithmetic, and printed numbers are cleaned of float noise. `production-read` returns `lines` {capacity, used, unassigned, pendingExpansion, contracts, clients, overAssigned, exact, basis, consistent, problems}: unassigned is exact from the product sliders (maxLines - manualLines) or from the desktop Production icon ("used/capacity"); `consistent` checks product rows against the displayed totals. `production-expand` verifies either the pending "(+N)" or a new project card (`verification`), which also works for large factories; `--count N` (CLI, 1..20) starts N identical batches one after another, stopping at the first failure. `market-catalog` and `sales-read` re-render an already open native table before reading (the game refreshes them only when opened, at month end or on a filter change), so your own price changes appear immediately (`refreshedBeforeRead`); the Specs table lists at most 50 CPUs per market (`rowLimit`).

Mod-synthesized notifications: the game has no popup for rival price changes, so the CLI diffs the Analysis tables (Desktop, Mobile, Industries) whenever `situation`, `market-changes` or `watch-advance` read them, and records notifications with `source: "cli_synthesized"`, `native: false` and ids `syn-N` in tools/competitor-prices.json. `pt-agent notifications` merges them (by game date) with the native popups; `--type competitor_price_changed` filters them. Types:
- `competitor_price_changed`: gameDate, sinceDate/referenceDate (when the reported old price was last reported), market/markets, company, cpu, oldPrice, newPrice, changePercent, mips, mipsPerDollarOld/New, previousSegment/segment (from the native recommended segment prices; when unknown, `segmentUnknownReason` says why), `impact` and `impactSummary`. Noise control: a notification is emitted only when the net move since the CPU's last reported price reaches the threshold, by default BOTH at least 2% AND at least $5 (a threshold of 0 disables that condition) (`--competitor-price-min-percent P`, `--competitor-price-min-dollars D` on watch-advance, situation and market-changes; `--competitor-min-change-percent` is an older alias). Smaller moves (for example daily $1 steps, or $5 steps of about 1% on an expensive CPU) accumulate silently and are reported once as one notification from the first old price to the latest price with `steps` and `rolledUp: true`. The impact describes the current position against your CPUs in that market: `impact[]` per own CPU with `rivalDominates` (at least the MIPS for no more money), `rivalBetterValue` (higher MIPS/$) and a `hint`; `impactSummary` lists them, e.g. "now dominates C52 (more MIPS, same price), C50 (more MIPS, lower price); better MIPS/$ than C52, C50, C54, C53" ("now" marks what changed with this move; "no longer ..." when a raise gives the position back). One notification per CPU per game day; a company that reprices 3+ CPUs at once gives one notification with `aggregate: true`, `count`, `direction` and `cpus` (each with its own impact); its `impact` is merged per own CPU ({ownCpu, dominatedBy, worseMipsPerDollarThan}) and its `impactSummary` is one short line per affected own CPU, e.g. "C52: dominated by Kore Ultra 3 115, Kore Ultra 5 245; worse MIPS/$ than 4 Inlet CPUs" (at most 5 CPUs listed). All generated texts use invariant number formatting (1653.43, never the OS locale's 1653,43); if one CPU changes twice on the same game day the notification is updated and reported again.
- `rival_took_lead`: a rival took the top-MIPS or best-MIPS/$ position in a market (or in a price segment where you sell), `tookFromPlayer` when it was yours. By default only when the leading company changes or the lead is taken from you; `--include-same-company-leads` (watch-advance, situation, market-changes) also reports a rival replacing its own leader (`sameCompany: true`).
- `player_took_lead`: one of your CPUs took such a position from a rival.
- `segment_price_changed`: a native recommended segment price moved.
- `unserved_demand_spike`: a market's unserved share rose 5+ points while rival CPUs left the table (retired or dropped out of its top 50).
- `research_time_dropped` (from situation's research reads) and `factory_expansion_completed` (watch-advance).
`market-changes` also reports `newRivalCpus` (popularity history of rival CPUs first seen after tracking started; Market view reads) and `segmentRecommendedPrices` per market. Rivals outside a table's top 50 are not tracked.

watch-advance additions (all optional; existing guards and output fields are unchanged):
- Competitor prices: `--track-competitor-prices end` (default: one table read at the end, dated by the stored snapshot range), `daily` (read after every day; Analysis is closed again so the pinned Production stays usable) or `off`. `--stop-on-competitor-price-cut-percent N` (implies daily) stops when a rival's price is N% or more below its price when the watch started (so a series of small cuts adds up; `change.comparedWith: "watch_start"`; each CPU triggers once per watch); `--competitor-price-scope near` limits it to CPUs within 0.5x..2x of a watched product's MIPS in its market or in its price segment. `--competitor-price-min-percent P` / `--competitor-price-min-dollars D` set the notification threshold described above. Segment prices are read at the start and end of a watch and at each month start. The result has `competitorPrices` {tracking, changes} and the notifications in `notifications`.
- Portfolio guards over ALL your products (not only the watched ones): `--stock-growth-days N` (stock rose N days in a row), `--idle-demand-below UNITS` or `--idle-demand-ratio-below R` (lines assigned but demand below UNITS/month or below R x production), `--stock-months-above M` (stock worth more than M months of current demand: old stock), `--any-demand-change-percent P` (day-over-day demand move of P% or more, with `likelyCauses`: own_price_change, own_sibling_price_change, own_release, rival_release, rival_price_change (daily tracking), month_rollover, or unknown). `--portfolio-guards` sets 7 days / ratio 0.05 / 6 months / 30% where not given. Idle-lines and old-stock guards fire when the condition newly appears; conditions already true at the start are listed in `portfolioFlags.atStart` and do not stop the watch. Triggers carry `scope: "portfolio"`.
- `--stop-on-expansion-complete`: a finished factory expansion (capacity up or pending "(+N)" down) always adds a `factory_expansion_completed` notification with `unassignedLines`; this flag also stops the watch there. `lines` in the result shows capacity/unassigned at the stop.
- `--monthly-digest`: at each month rollover the watch adds a `game monthly-digest` snapshot to `digests` (it does not stop).
- `priceFollowUps`: price changes made with `--follow-up-days N` are reported by the first watch-advance or time-advance on or after their due date (demand of the product and its same-market siblings then vs. now, and market share when known).

Pricing and lines (explicit commands only; warnings never block and nothing is decided for you):
- `game product-price NAME --price P` now checks before committing (sales sheet, the product's market table and segment prices): `below_unit_cost` (with `estimatedMonthlyLoss` at current volume), `supply_limited` (a cut adds no units while the product sells all it makes), `segment_threshold_crossed`, `dominates_own_product` / `cannibalizes_high_volume_sibling` (the new price makes it at least as fast for no more money than your sibling) and `dominated_by_own_product`. `--dry-run` returns only `check` (nothing changes); `--skip-checks` commits without the checks (the previous price is still read from the sales sheet and recorded, so price-revert works); `--follow-up-days N` schedules a follow-up. The committed result keeps the native fields and adds `oldPrice`, `check`, `priceHistoryRecorded`.
- `game price-history [NAME] [--limit N]` lists CLI-recorded changes (tools/price-history.json; product-price, price-probe, price-revert and plan-apply) and pending follow-ups; `game price-revert NAME [--steps N]` sets the price from before the last N-th recorded change.
- `game product-production NAME --add N` (relative, may be negative), `--lines max` (current manual + all unassigned) and `--clamp true` (use the nearest allowed value instead of failing) resolve an absolute value from the native slider range first (`linesResolved`).
- `game plan-apply --file plan.json [--dry-run] [--clamp] [--rollback-on-failure]` with {"items":[{"product":"C5","price":199},{"product":"C6","lines":12},{"product":"C7","add":-3},{"product":"C8","lines":"max"}]}: validates everything first (unknown products, line pool after the plan's decreases, prices 1..9999) and changes nothing if any item is invalid; then applies line decreases, line increases and prices in that order, each with native readback (`steps[].old/new/readback/verified`, price `warnings`). It stops at the first failed step (`failedAt`); `--rollback-on-failure` restores the applied steps.
- `game cleanup-preview [--demand-below N]` (reads only) lists products with little demand, their lines, stock, unit cost and `estimatedLiquidationValue` (retirement sells stock at roughly unit cost; `product-preview NAME --retire true` gives the exact native quote and contract fines).

Other compositions (reads only unless stated): `game monthly-digest` (share and change per market and segment vs. the previous digest, rival events of the last 31 days, largest own supply/demand gaps, idle lines, stock value, headroom/runway, completions within 45 days); `game research-funding-compare --funding-percents 25,50,100` (time must be paused, except in a Multiplayer session, whose shared clock keeps running: each level is then read within about a second and the note says so; sets each level on the active research, records monthly cost, speed, days left and estimated remaining cost, then restores the original funding and verifies it); `game cpu-preview --die-sizes 10,15 --frequencies 3.2GHz,3.5GHz --core-counts "Single Core,Dual Core" [--planned-price P]` is routed to `cpu-variants` (one table with MIPS, power, temperature, yield, unit cost now and later, estimated units per line; max 60 combinations; the draft is restored). Frequencies are in MHz like --frequency-mhz; unit suffixes (3.5GHz, 3500MHz, 800KHz) are accepted, and a bare value below 100 is read as GHz when the draft already runs at 100 MHz or more (late game), otherwise as MHz (early game); `frequencyUnits` in the result says which.

Quitting: `pt-agent quit` (no --endpoint; it always acts on the local game) exits the game client WITHOUT saving through the native Pause Menu "Exit To Desktop" path (it accepts only the known "unsaved progress will be lost" confirmation); `--save NAME` creates a native save first and aborts the quit if that fails. It refuses while a native dialog (release form, completion popup) is open or a time advance is running. The bridge usually drops the connection or sends an empty or partial reply while the game exits; that is expected, and the outcome is decided by polling the process. It always prints one JSON result: `ok`, `outcome` (process_exited, still_running, not_running, unknown), `route` (native_exit_to_desktop, native_exit_then_window_close, window_close), `processRunning`, `saved` and `steps`. If the in-game path fails or the bridge is unavailable, it asks the game window to close (like its close button); it never kills the process. It never runs automatically.

CPU windows: `cpu-options` and `cpu-select` close the picker they opened, and `cpu-options` also closes the CPU designer when it only opened it to list options (the draft's settings persist; `--keep-open true` keeps them, `--close-designer true` also closes the designer after cpu-preview/cpu-select). `cpu-review` and `cpu-develop` reopen a closed designer on the saved draft first (`reopenedCpuDesigner`). Any game command refused with `not_interactable` now lists `blockingWindows` and the exact window-close commands.

### CPU Game API

```
pt-agent game cpu-schema
pt-agent game cpu-preview
pt-agent game cpu-preview --name "Trial One" --frequency-mhz 0.5 --die-size-mm2 15 --l1-cache-kb 0
pt-agent game cpu-preview --file cpu-draft.json
pt-agent game cpu-read
pt-agent game cpu-options architecture
pt-agent game cpu-select architecture --value CISC
pt-agent game cpu-select memory --value "DIP SRAM" --show-obsolete true
pt-agent game cpu-review "Trial One" --target-market Desktop --planned-price 100
pt-agent game cpu-develop "Trial One" --review-id REVIEW_ID --decision-reason "Current market comparison and funding rationale"
pt-agent game cpu-develop "Trial One" --review-id REVIEW_ID --acknowledge-risks far_below_market_performance --decision-reason "Why this risk is acceptable and how it is handled"
pt-agent game cpu-options process-node --value -3
```

Example cpu-draft.json: `{"name":"Trial One","frequencyMHz":0.5,"dieSizeMm2":15,"coreCount":"Single Core","l1CacheKB":0}`. `--json` accepts an inline JSON object; `--file -` reads JSON from stdin (often easier than shell escaping). With PowerShell: `@{name='Trial One';frequencyMHz=0.5} | ConvertTo-Json -Compress | .\tools\pt-agent.exe game cpu-preview --file -`.

Prefer named flags for ordinary CPU edits: `--name`, `--frequency-mhz`, `--die-size-mm2`, `--core-count`, `--memory-controller`, `--l1-cache-kb`, `--l2-cache-kb`, `--l3-cache-kb`, `--overclock true|false`, `--smt true|false`, `--automate-cache true|false`. JSON/file/stdin remains useful for generated payloads; both forms use the same API. A field cannot be supplied twice. Numeric flags use decimal dots independent of OS locale.

`cpu-preview` opens/reuses the CPU form, edits ONLY supplied fields, leaves it open and returns the updated draft. Supported fields: name, coreCount (exact current dropdown label), memoryController (exact label), overclock/smt/automateCache (booleans), frequencyMHz, dieSizeMm2, l1CacheKB/l2CacheKB (per core), l3CacheKB (shared). Availability, dropdown options and slider ranges come from current UI, not a hardcoded technology list. Disabled currently does not mean unsupported forever. Native transformations can alter other draft values; the response contains actual results. Unknown parameters fail before navigation. Numeric values target native displayed precision via bounded visible slider search; an unreachable value restores that slider and reports an error, while earlier edits may remain.

Hardware selection uses `cpu-options KIND` with package/process-node/architecture/memory, then `cpu-select KIND --value EXACT_NAME` (e.g. `cpu-select architecture --value CISC`). It opens/reuses that catalog and selects the exact native card, including offscreen cards. The old `cpu-select HANDLE` remains a compatibility form, not the preferred ordinary workflow. Properties are the player-browsable card texts (including native cost, time, markets, royalties etc.), not hidden data. Lists include the complete active filtered catalog unless marked truncated; no manual scroll is needed. Filters: `--show-obsolete true --licensed false` (subject to native availability). Licensed names retain their company suffix. `cpu-select KIND --value NAME --show-obsolete true` (and/or `--licensed true`) sets those picker filters first (CLI; the result reports `catalogFilters`). When cpu-select cannot find a card, the CLI checks whether the Show Obsolete or Show Licensed filter hides it, restores the filter, and returns the exact retry command in `error.hint` / `next`. Selection invokes the card and native Select in order, closes that transient picker, then returns the recomputed CPU draft. The CPU draft remains open with its edited settings; `game window-close Create CPU` closes only that form through its native Close button. No other open selectors, dialogs or drafts are silently dismissed.

`cpu-read` reads the already exposed CPU form without opening/editing anything. Results distinguish total project cost and monthly project expense; numbers are derived from rounded display text, not exact internals. Development has NOT started. `cpu-review` does not advance time or commit a project; its dated `reviewId` is bound to the current draft and finances. Commit separately with `game cpu-develop EXACT_DRAFT_NAME --review-id ID --decision-reason "your reason"` (add `--accept-missing-evidence true` only if needed). Without a review, `cpu-develop` returns `review_required` before native input. A changed date, draft or finances requires another review. A new visible project row proves `development_started`; otherwise the result reports `confirmation_required` or `input_dispatched`, not assumed success. Resolve native confirmations explicitly. Game time is not automatically paused.

Multi-step game commands are ordered, honor agent pause and the user-selected action delay, stop on errors or observed local player input, and never blindly replay. Partial failures describe the stopped step; earlier form edits remain. An operation ID remains queryable if your CLI times out. Tray feed identifies commands as `/cpu-preview`, `/cpu-options`, `/cpu-select` rather than flooding the feed with internal slider probes; detailed steps remain in the journal. UI mappings are verified against the English 0.2.16a5 form, not a guarantee for future versions.

### Detailed Generic UI

Use `pt-agent observe`, then `pt-agent ui click|set|select|scroll|hover HANDLE ...`; `ui inspect` is optional when the observation is sufficient. Add `--observe SCOPE` (or `--observe screen`) to an action to receive the new observation in its result, avoiding a separate observe call. These commands discover the CURRENT game UI rather than assuming a fixed game-specific script. Standard controls in new game windows can therefore work without a new workflow adapter. No screenshots or access to AGENTS.md is required.

Generic output groups sibling texts, labels sliders with their native displayed values, and returns current values, actions, options and reachability. Handles stay stable across unchanged observations. An edit/inspect returns a refreshed handle if the control changed; use that handle for follow-ups. Do not memorize handles across reloads or guess them. `observe --scope TEXT` focuses on a window/path; `--offset N --limit N` pages the result. `ui inspect` gives full control details. `elapsedMs` measures observation cost.

## Choosing generic vs adapters

- DEFAULT for ordinary supported gameplay: Game API, including navigation/settings/saves/dialog commands. Generic is fallback for unmapped/new controls, modified UI and diagnosis.
- A component adapter can make a table, graph, custom slider or dynamic tooltip easier to read without adding a separate command for every screen.
- A workflow adapter can combine repeated game-specific steps into one command, but depends more on that mechanic and version. Use one ONLY if `capabilities` actually advertises it and its documented behavior fits the task.
- CPU, research/projects, products/production, contracts/business, market/Inspector, hardware and session/settings workflows are covered by the Game API. Use advertised commands. Disabled native stubs and dormant Calendar/Wiki are not exposed through forced activation; future/modded content may need Generic.
- Report concrete shortcomings (ambiguous units/labels, unsupported widget, missing game command). Use Generic when needed, not as a mandatory intermediate step for supported gameplay.

`pt-agent guide` and `pt-agent help` work even when the game is closed.

```
pt-agent status
pt-agent capabilities
pt-agent observe --limit 60
pt-agent observe --scope Settings
pt-agent observe --scope Settings --changes
pt-agent events --since 0
pt-agent ui inspect HANDLE
pt-agent ui click HANDLE
pt-agent ui set HANDLE --value "My company"
pt-agent ui set HANDLE --value true
pt-agent ui select HANDLE --value "Windowed"
pt-agent ui scroll HANDLE --value -1
pt-agent ui hover HANDLE
pt-agent ui focus HANDLE

pt-agent screenshot

pt-agent agent resume --explicit-user-request
pt-agent agent delay --value 250 --explicit-user-request

```

Use the actions shown for that control. `set` takes input text, boolean toggles, or a RAW slider value within the reported raw range. A raw slider value is NOT necessarily the physical value displayed by the game; check the adjacent display text, adjust and re-observe. `select` takes an exact displayed option label (or zero-based option index). Text input commits through the field's normal edit/validation lifecycle; the game may normalize it. `scroll` uses mouse-wheel units, positive up, negative down. `hover` invokes pointer enter for native tooltips; query again after their native delay.

Observations filter inactive, transparent, offscreen and masked UI, and use draw order and rendered Image/RawImage geometry to filter opaque foreground coverage, including non-interactive backgrounds. Partially hidden TMP text is returned as visible fragments with `…`; do not interpret fragments as complete names or numbers. Fully covered controls are omitted. Transparent hit areas do not hide text, but remain discoverable as controls when native pointer input can reach them. This is not pixel-perfect shader/texture analysis: unusual sprites, custom graphics and transition frames still need a screenshot if ambiguous. After loading/navigation, re-observe before interpreting values; UI settling does not prove asynchronous game initialization. Native unfilled forms can display placeholder zeros: select the relevant item before interpreting them as gameplay values. Covered controls are not actionable; close/focus the relevant window through its real controls first. Text is formatted UI information, not exact underlying numeric precision. Reading itself does not open or close windows. Prefer one full overview, then targeted `--scope` reads.

For visual inspection use `screenshot`: it captures the rendered game INCLUDING the agent tray, without the desktop or other applications. The response contains a local PNG path, dimensions and capture frame/time. Default is a temporary `latest.png`, replaced on the next capture and removed on game exit. `--output PATH` preserves a copy (overwrites that explicit path). Prefer structured observe for gameplay; use screenshots for layout, graphics or ambiguous controls. Screenshot is not an OCR command.

Observations include `surfaces` with current window titles and scopes; use these scopes instead of guessing window names. Control `window` gives human-readable context; `details` preserves extra button text. Values grouped with `|` follow approximate screen reading order and are not inferred table columns. Losing OS focus is supported; minimized/Windows-hidden rendering is not guaranteed.

`name` is the humanized Unity object name, useful when a button's visible `label` changes to a status (for example a capacity count); it is not a guaranteed cross-version semantic ID. Text records sharing `group` belong to the same repeated UI container/row; controls within repeated rows also expose `group`, linking row actions to their text without guessing from identical labels. Group IDs are runtime-only, not persistent identifiers or clickable handles. `ui inspect` includes screen-pixel bounds (origin bottom-left) for verifying window movement. Both `--value X` and `--value=X` are accepted.

Only `handle` is an action target (format `instance:number`). `id` (`u...`) and `group` (`g...`) are identities for linking/diffs, NOT handles. Unchanged handles survive observations, including unrelated scoped reads; changed/removed controls still require a refreshed handle. Use sequential mutations: parallel close/open calls have no guaranteed intended ordering. `--observe` supplies the next handles in the same round trip, but still does not prove asynchronous scene loading is complete.

`agent panel --value true|false` opens/closes the mod's Agent window for visual review (`--value about` also opens the About window with the version, credits and project links). It does not change game windows or resume the agent. The mod's own overlay never blocks agent commands.

Covered popups: a native popup can end up behind windows opened after it (a workspace opened over it, or a form you kept editing while a Multiplayer clock ran and a research completed). `dialog-read` still lists it with its text and choices and `covered: true`, `window-list` shows it under `coveredWindows` with `dialog: true`, and `dialog-choose` first brings it to the front (as clicking it would) and then presses the choice. Research commands refuse to open the full-screen Research window while a popup is open, so they cannot bury it.

Modal time-resume edge case: a completion popup can pause game time while remembering the previous speed. Closing it resumes that speed; a separate Pause command may arrive after extra game ticks. Even two dispatches in one frame cannot guarantee safety because the game removes its blocker during a later Update. Do not promise a zero-time close-and-pause transaction. Research Completed has a native `Select New Research` action that explicitly chooses pause; prefer this paused continuation when appropriate, then close the research window if desired. Other popups need their own native behavior checked; never bypass their blocker. Agent pause is NOT a substitute for game-time pause.

`ui focus` dispatches native pointer-down/up without click to a reachable control/header; `ui drag --value "dx,dy"` dispatches a native drag in screen pixels, positive right/up. Only use advertised actions. Some covered windows require closing the foreground modal first. Commands wait for several stable local text/scroll-position frames (bounded); `uiSettled` is a UI observation, not proof of a gameplay outcome.

## Execution and outcomes

JSON is written to stdout; local usage errors go to stderr. `--endpoint http://127.0.0.1:PORT/` selects an instance explicitly; otherwise use the local endpoint file near the CLI. Mutation responses identify an operation. `accepted` or `running` is NOT completed: query `operation ID` until finished, or use the CLI's default short wait. Never blindly repeat a timed-out mutation. The result may say `partial_failure` if input was dispatched but completion could not be verified. Re-observe rather than assuming rollback.

The player may interact concurrently. `context_changed` / `stale_target` means observe again before choosing the next action. `not_interactable` means the current UI does not permit that action. Native dialogs belong to gameplay; inspect and respond to them yourself within the player's request. No extra per-action human approval is required.

Normal `observe` is quiet: `updates` appears only when new local player input was observed since this session's previous observation, condensed to a count and last target. Treat it as a reason to re-check the affected UI, not proof the player caused every change. Agent-issued native events are not reported as player device input. Keystroke content is NOT logged. `status.activity` gives last input and OS focus; `events --since ID` explicitly retrieves the bounded 128-event journal and reports history truncation. It records local input and agent commands, not a spammy stream of simulation ticks. Nothing about these background changes is added to the on-screen feed.

For diagnosis use `observe --scope WINDOW --changes`: differences are relative to the previous observation with the SAME session/scope/offset/limit. `id` identifies a live control across refreshed action handles, not across reloads. Text group IDs are runtime-only. Changed text may be periodic simulation/UI updates; its cause stays unknown unless independently established. Detailed differences are opt-in, capped at 40 with an omitted count, never interpreted as a causal event log.

The game keeps running while you think unless YOU use its normal pause/speed controls. The mod's agent pause is separate from game time. On `paused_by_user`, STOP issuing game actions. Use `wait-until-resumed`; a timeout means still waiting, not permission to retry/resume. After resume, re-observe and reconsider unfinished work.

Change action delay or resume yourself ONLY ON EXPLICIT USER REQUEST. `--explicit-user-request` records your assertion, not independently verified permission. Do not add it on your own to bypass a pause. Default extra action delay is 0 ms; readiness waits still apply.

`--hidden` is an explicit requirement, never permission to silently execute visibly. Current generic observations are non-invasive and support it; current UI mutations do not, and return `hidden_not_supported`. Game API uses the workspace ownership/cleanup policy described above; Generic never automatically closes windows.

## Connection and feed

The client sends a logical session identifier. Commands and live waits renew a five-minute activity lease; `Connected` means a recently active client session, not proof that a model is thinking. Expired sessions are shown as inactive. There is no background LLM runner in the mod.

The action feed records factual operations; an `agent say` entry is marked as an agent message. Repeated reads can collapse to xN. No chat input or OpenRouter is included.

## Multiplayer (optional mod)

When the separate Processor Tycoon Multiplayer mod is installed, `status` includes a `multiplayer` object (`active`, `state`, `host`, `slot`, `canControlTime`, `players`, `lastCheckpointDay`, `resyncs`, `resumable`, `error`). `pt-agent mp status` returns the same object; without the mod, `mp` commands fail with `multiplayer_not_installed`.

- `pt-agent mp host [PORT] [--value NAME]` hosts the currently loaded game (start or load a campaign first). `pt-agent mp join IP:PORT [--value NAME]` joins from any screen; the shared world then loads (poll `mp status` until `state` is `Running`). `pt-agent mp resume [SESSION]` hosts a saved session from this machine's latest checkpoint. `pt-agent mp leave` ends the session. `pt-agent mp chat TEXT` talks to the other players; `mp chat "@Name TEXT"` sends it to one player only (an unknown name fails with `chat_not_sent`). Messages from other players arrive in every reply's `notifications` as `chat_message` items (`from`, `private`, `text` "Name: message"), like the game's popups; answer them between actions. `pt-agent mp chat-read` returns the whole recent conversation with your own lines (`--since N` after line number N, `--limit N`). Private messages from players and their business-deal proposals arrive as emails (`game email-list`, `game email-read`): a proposal lists every term and shows the Email window's Accept and Decline buttons (press one with `ui click` after `observe`); unanswered, it is declined automatically after 30 game days.
- In a session, only the host controls game time. On a non-host machine `game time-set` fails with `multiplayer_host_controls_time`, and `game time-advance` / `projects-wait` can only wait: days advance at the host's pace, so the result may stop later than requested. Native dialogs and open forms (the CPU designer) do not pause the game in a session, so time keeps running while you read or design: close popups promptly. A `cpu-review` stays valid for `cpu-develop` for 3 real minutes as long as the design (settings and chosen hardware; the process node's daily maturity % is ignored) is unchanged; a `context_changed` names the field that moved. Transient notification toasts do not block commands. A bankrupt player stays in the session as a spectator (`companyBankrupt.source: multiplayer_session`, `mp status` `bankrupt: true`).
- **Playing alongside the user (companions).** When the user wants you as another player in the session they host in this game, never play through this installation: its CLI controls the user's own game, and `mp join` here would take the user's game out of their session. Ask the user first, then run `pt-agent companion start NAME --explicit-user-request [--company "Company Name"] [--company-type cpu|fabless|foundry]` with this installation's CLI. It copies the game into `CompanionsNAME` (own settings, bridge port and multiplayer identity), starts it without a window (`--windowed` for a small visible one), joins the user's session through its local address (also when they host on Steam) and founds your company as a new game started now. The reply's `cli` is your CLI from then on (for example `"<cli>" game situation --compact`); screenshots do not work without a window. Several agents can play at once, each with its own NAME. `companion list` shows them; `companion stop NAME` leaves the session and closes that copy (its company stays in the world under the host's caretaker rules; `companion start NAME` returns to it). The user must host (Multiplayer window, Host a game); without a running hosted session `companion start` fails with `no_session`.
- Every player owns only their own company. Rival human companies appear as ordinary competitors (market share, notifications). Contracts are one shared pool (the host decides tenders; offers from any player count); business deals with AI companies work for every player; a deal with another player becomes a proposal they accept or decline.
