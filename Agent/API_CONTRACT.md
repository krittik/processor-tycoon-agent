# Game API implementation contract

Status: approved design direction; implemented commands are only those in capabilities/guide. See CHANGELOG.md for the current version. Target English Processor Tycoon0.2.16a5; future/modded UI must fail honestly and leave Generic usable.

## Agent ergonomics

USER ACCEPTANCE CLARIFICATION: a Game API command must solve an agent's gameplay task, not just wrap one UI widget. Routine callers must NOT manually pan trees, scan scroll pages, inspect object paths or juggle generic handles. Module owns visible navigation/search/pagination and postcondition reading. A currently-visible-only list can be an honest intermediate implementation, but is NOT completed domain coverage. Provide a complete player-browsable catalog (including currently unavailable future choices) where planning requires it, and simple filters/search. Never label an incomplete scan complete; explicitly surfaced limits remain open work, not justification to push routine work back to the model. Do not expose secrets that the game actually hides. Cache observed catalogs with scene/version/state validity and refresh dynamic availability/costs at action time.

- Ordinary gameplay should not need generic handles: semantic commands, exact entity names from lists, physical units. Never pick the first of multiple name matches. A native control label is not automatically a persistent entity ID.
- Keep unique names as the default. If ordinary native entities can share names, their list must expose an explicit domain reference accepted by the same domain actions; do not tell the caller to rename an entity that the API itself cannot select. References may use current rendered UI identity, scoped to the game run/scene; state their lifetime and reject stale references rather than guessing a same-name replacement. This is targeted disambiguation, not a return to Generic observe/handle juggling for routine unique-name actions.
- A reused native UI row is not stable entity identity. A domain may compare reference equality of objects already bound to its rendered UI controls solely to disambiguate current entities; do not read fields/properties/IDs or invoke methods on those underlying simulation objects. Tokens must be revalidated against current UI bindings, scoped to run/scene and cleared across scene replacement. This narrow identity exception does not expose hidden gameplay information or authorize cross-domain model joins.
- CLI syntax for this iteration: `game DOMAIN-VERB [EXACT_TARGET] --named-option VALUE`; flat command names keep existing CPU commands compatible. Request.Command is `game.domain-verb`, Target carries the entity name, Parameters contains camelCase typed values. Root integrates CLI flags centrally. JSON/file/stdin remains available for structured/generated payloads, not mandatory shell boilerplate.
- Provide list/read/preview before set/start/commit. Explicit start/commit commands perform native commitments; do not force the caller back to Generic. The user-approved CPU review gate requires a fresh evidence review and the agent's explicit reason before `cpu-develop`; it reports risks without vetoing the agent's decision. No extra human approval or automatic business/affordability decisions. NEVER start development from preview or infer approval from a read.
- Compact normal responses contain actual state, available choices/disabled reasons, typed quantities when unambiguous, and a concrete next command when blocked. Retain native display alongside rounded-derived numbers where useful. Do not emit entire generic trees, internal handles or per-slider traces on success. Detailed Generic and event journal remain available.
- Read is not permission for hidden-data access. Game reads MAY open the requested visible window as documented. `--hidden` must reject such navigation, not silently flash a window.

## Native execution boundary

LATEST USER OVERRIDE (takes priority over earlier stricter wording below): literal player click flow is NOT more important than agent usability. Game API may use narrowly compiled semantic adapters: enumerate the complete current player-browsable UI catalog including offscreen cards, read their displayed UI data, and invoke the same native player action without requiring viewport pan/click choreography. Generic remains literal visible UI. Research example: active ResearchTreeWindow contains instantiated ResearchButton UI cards; reading serialized TMP/InfoText and native interactable/lock/researched UI markers is allowed, reading TargetTechnology/ResearchDataProvider simulation secrets is not. Narrow reflection binding to these explicit UI fields is allowed if needed, not arbitrary reflection/API script evaluation. Preserve game rules, technology locks, native disabled state, modal decisions and real side effects; open relevant window/show result for player. Do not retain a literal-UI limitation as the permanent Game API design.

Semantic mutation execution: yield `GameUi.NativeStep(label, () => { ... })`. This creates Request.NativeAction marked JsonIgnore, inaccessible to HTTP callers; only reviewed compiled module code can supply it. Root scheduler retains pause/input conflict/ordered dispatch/delay/journal and yields native update frames. Revalidate exact UI identity and native enabled/lock state INSIDE the callback; verify result afterward. This is not permission to bypass an unrelated modal, mutate hidden simulation fields, silently alter locked tech or infer game success from callback return. Prefer existing yielded ui.* where equally convenient.

For a semantic action with a real UI control, use `GameUi.NativeStep(label, action, component, visualClick)` to provide its decorative cursor target. Scheduler validates current literal visibility/enabled/raycast position before dispatch and displays the cue only after the native callback returns successfully. No delay; no guessed screen coordinates, fake offscreen clicks or serialized Unity objects. Omit target for an action without a single truthful control.

- Use GenericUi native events or reviewed narrow native player-UI actions: no Assembly-CSharp references, reflection into hidden simulation data, fabricated research unlocks, or copying formulas as displayed knowledge. Desktop workspace navigation may preserve overlapping ordinary player windows, but never bypass modal decisions or native disabled states.
- Local decompilation is allowed to understand UI names/semantics, not as an implementation dependency or to expose unrevealed data.
- Module implements IGameModule in its OWN file: Commands, Validate(Request), Prepare(Request):IEnumerable<Request>, Result(Request):JObject. Shared GameUi.cs supplies normalized Generic reads and unambiguous control matching. Root owns Plugin, CLI, shared helpers and registry.
- Validate types and known keys before any navigation. Prepare yields native `ui.*` requests ONE AT A TIME; after yield the scheduler executes/settles, then next MoveNext can re-read UI. Do not cache action targets across previous mutations. Result runs after final step. Never call ui.Act directly. No sleeps, nested coroutine scheduler, thread/task work touching Unity, or separate HTTP calls inside a module.
- Root scheduler provides pause, action delay, player-input conflict, sequential dispatch, operation IDs, terminal errors and feed `/command`. Errors are AgentError(code,message). No blind retries or rollback claims; previous steps may remain. Reads/lists are still serialized when they navigate.
- Never silently close unrelated windows, overwrite player edits, dismiss arbitrary dialogs or resume game time. Normal native confirm/close effects are allowed but must be reported. Explicit navigation close/dialog commands handle such situations without requiring Generic.
- Native confirmations: commit opens the REAL confirmation and either explicitly handles the expected known confirmation for that command, or returns its choices and `confirmation_required`; do not report the business action complete merely because its first button was clicked. Shared `dialog-read`/`dialog-choose` handles recognized native dialogs and exact returned choice labels. Unknown confirmation must not be auto-accepted.
- UI settling is not business proof. Verify the appropriate postcondition (selected value, project row, native success dialog). If unverified, return `outcome: input_dispatched`/pending with next inspection, not a false success assertion. Detect async scene loading separately.
- Lists enumerate the complete active player-browsable UI catalog where instantiated cards expose it; virtualized lists require evidenced native traversal and explicit partial/truncated status until complete. No hidden inactive content or guessed table columns.
- Technology-dependent controls/choices are live; disabled != permanently unsupported. Numeric units/step sizes depend on current UI. Do not infer min/max physical ranges from raw slider limits.

## Parallel implementation and acceptance

- Sol medium, fresh no-history. User clarified omission of priority requests ordinary mode; do not explicitly request priority for Sol. Luna medium fresh independent tester may use priority; tool has no service-tier selector, so actual backend tier cannot be independently asserted.
- Each worker owns its module and a short `api-notes/DOMAIN.md` with commands, native mapping evidence, limitations and test proposals. No edits to shared files, build/deploy/restart, gameplay inputs, or memory unless root assigns them. Read-only decompilation is independent; live client belongs to root while workers code.
- Do not invent missing UI hierarchy paths. Inspect existing evidence, decompile relevant UI types, request root snapshots if needed. Mark uncertain mapping explicitly. Compile locally only if not competing with root build; prefer root integration build.
- Root reviews input routes, scope/identity matching, no hidden data, error/partial semantics and actual state readback; then serial live tests. Use small representative checks, not an exploding test suite. Full coverage requires lifecycle evidence, not just one command per screen.
- Coding style: concise C#, no needless defensive wrappers, simple statements one line, do not split method args unless needed. Agent usability outranks clever abstractions. Keep version mappings isolated.

## Shared helper API (implemented)

`new GameUi(GenericUi)`; `Read(scope)` -> JObject generic snapshot (up to200 controls/texts), `Native` for Validate/Inspect if truly needed.
Static helpers: `Controls(view)`, `Texts(view)`, `One(candidates,description)`, `Find(view,name,role?)`, `Click(node)`, `Set(node,JToken)`, `Select(node,string)`, `Action(command,node,value?)`, `Parameters(request,params string[] keys)`, `RequiredTarget(request)`, `Compact(view)`.
Compact is a baseline for diagnostics/simple forms; domains should add useful normalized rows/entities rather than wrapping a wall of text as a supposedly semantic API. Native values on generic sliders are RAW; do not relabel them as units.
